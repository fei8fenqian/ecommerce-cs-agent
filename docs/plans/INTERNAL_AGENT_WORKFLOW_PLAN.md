# 企业电商中台：内部 Agent 工作流计划

> 状态：当前执行计划（2026-08）。客户侧商城、聊天、下单、沙箱支付/退款和售后初版已经存在；后续优先交付内部员工能实际使用的 Agent 工作流。

## 1. 产品定位

这不是给每个角色再做一个聊天框，也不是让员工把聊天回答复制到业务系统。目标是让 Agent 在授权边界内主动发现、归集和推进日常/周常任务；员工只处理金额风险、争议、事实不完整和需要判断的例外。

每条工作流必须说明：

```text
触发条件 → 可读业务事实 → Agent/规则动作 → 业务状态或待办 → 成功结果 → 超时/失败/人工升级
```

系统数据库中的订单、支付、退款、履约、工单仍是唯一业务事实；飞书只负责通知和协作入口。

## 2. 当前基线

已经可复用：客户门户、聊天和 RAG、工单及消息、AI 工单处理、客服认领和回复、结算订单、支付宝沙箱支付/退款、财务退款审批、运营发货队列、JWT/Casbin、审计、Redis/PostgreSQL。

已经实现但尚未完成真实演示：高风险工单的去重升级记录、飞书 Webhook 脱敏卡片和重试 worker；本轮已补客服工作台通知状态和 SPA 登录深链。当前仍缺少飞书测试群配置、外部可访问的内部工作台地址，以及该链路的真实验收。

不重新建设通用 Harness、通用任务平台或任意飞书写工具。只有在至少两条已上线工作流确实重复需要持久化执行、重试或审批时，才抽取公共能力。

## 3. 部门交付顺序与工作流优先级

先按部门交付完整闭环，不把物流/仓储作为运营第一期范围。运营第一期只做商品经营、售后/退款经营分析和内部经营例外；发货、拣货、库存盘点、物流催办留到后续有明确业务数据和责任人后再做。

| 优先级 | 为谁省下什么工作 | 闭环与 Agent 边界 | 首次验收 |
| --- | --- | --- | --- |
| P0 客服 | 客服不必反复刷新人工队列、漏看投诉和资金类诉求 | AI 处理低风险知识问题；无法安全处理时创建待认领工单并通知飞书；客服在工作台认领、回复、关闭 | 发起“退款/投诉/转人工”工单后，一条脱敏飞书通知送达；客服认领并完成回复；不重复通知、不丢单 |
| P0.5 客服班前摘要 | 班前不必逐页查找超时、未认领和高优先级工单 | 确定性扫描当前待处理工单，Agent 只生成摘要和建议排序；不更改工单归属或状态 | 每日一条飞书摘要；链接进入筛选后的队列；重复运行不刷屏 |
| P1 财务 | 财务不必手工比对退款、支付结果和待审批项 | 以支付/退款事实生成待办；Agent 解释差异、汇总证据；批准/驳回仍由财务和确定性退款服务执行 | 一笔异常或高风险退款进入队列，财务看到金额、原因、状态和操作结果；重复操作不重复退款 |
| P2 运营 | 运营不必手工汇总商品、退款和售后异常 | 固定口径计算商品销量、退款/售后原因和低库存风险；Agent 生成日报、异常 SKU 清单和建议，不直接改价格/商品/库存 | 运营每天收到一份可追溯日报，并可将一个异常 SKU 创建为运营待办 |
| P3 管理层 | 主管不必手工拼接客服、财务和运营周报 | Report Service 固定计算口径；Agent 基于指标写周报和风险提示，不能编造数值 | 一份带时间窗、数据截止时间和指标来源的周报，可从工作台/飞书查看 |

仓储/物流是后置候选：待出现可信的仓库库存、出库和物流轨迹数据，以及明确的仓储责任人后，再单独规划“发货 SLA/缺货/物流异常待办”闭环。P1、P2 可并行准备只读查询，但不提前建立大而全报表平台。

## 4. P0：客服值班升级与飞书协作

这是下一条必须收口的业务闭环。

```text
客户创建/追问工单
  → AI Worker 原子领取
  ├─ 有可靠知识且为低风险问题
  │   → AI 回复 → 已处理
  └─ 退款、支付、订单修改、投诉、明确要求人工、知识不足或模型不可用
      → 写入升级说明 → 待人工处理
      → 同一事务创建唯一 escalation 记录
      → 通知 worker 投递固定飞书卡片（失败退避重试）
      → 客服从工作台认领 → 人工处理中 → 回复/关闭
```

卡片只包含工单号、紧急度、原因码、脱敏摘要、创建时间和内部工作台链接。不得包含客户 PII、完整订单号、支付/退款详情或完整对话；飞书内不做直接认领或资金操作。

实施顺序：

1. [x] 修正可从飞书打开的客服工作台 SPA 登录深链；配置测试群 Webhook 与 worker 开关。
2. [x] 在工作台显示通知状态（待投递、已送达、重试中、投递失败），但不暴露供应商响应或客户原文。
3. 用真实测试群跑通一次 P0；验证重复触发、飞书失败、已认领后客户追问三种危险路径。
4. 复用同一投递能力增加 P1 每日摘要，不另建第二套通知表或 worker。

## 5. P1/P2 的实现方式

### 财务：异常待办，而非“财务聊天机器人”

- 触发：退款待审批、退款处理超时、支付回调未知、对账差异。
- 事实：结算订单、支付交易、退款及审批记录；不得使用聊天/RAG 推断金额或到账结果。
- 动作：确定性服务创建或更新异常待办；Agent 只生成差异说明和证据摘要。
- 人工边界：财务批准、驳回、重试退款；回调/对账决定最终资金状态。

### 运营：商品与售后经营例外，而非泛化经营分析

- 触发：退款率/售后量异常 SKU、商品连续无销量、库存低于运营阈值、活动后转化异常。
- 事实：商品目录、订单、支付、退款、售后聚合 read model；每项指标附带时间窗与数据截止时间。
- 动作：系统按规则排序并生成日报和异常 SKU 清单；Agent 生成原因摘要和建议。
- 人工边界：调价、上下架、活动策略、库存调整均通过既有确定性服务；Agent 不直接写价格、商品或库存。

P1/P2 先各完成一个每日扫描任务和一个处理入口；只有实际出现跨请求等待、重试、审批恢复的重复问题，才增加最小持久化任务模型。

当前进度：财务只读异常扫描和工作台队列已完成，覆盖退款待审批、退款失败、退款处理中超时、支付长时间未完成；尚未自动改变任何资金状态。下一刀才是定时执行、基于本地事实生成证据摘要，以及按需推送飞书财务摘要。

## 6. 当前实现差距

| 部门 | 已有能力 | 与本计划的差距 | 下一步最小切片 |
| --- | --- | --- | --- |
| 客服 | AI 工单处理、人工认领/回复、升级记录、飞书通知 worker、工作台通知状态 | 未配置真实 Webhook；外部深链未部署验收 | 配置测试群并跑通一次真实 P0，验证失败重试和不重复通知 |
| 财务 | 退款列表、审批/驳回、沙箱退款状态、只读资金异常队列 | 没有定时执行、对账 read model、Agent 证据摘要或每日汇总 | 先验证异常队列，再增加定时扫描和可追溯证据摘要 |
| 运营 | 商品目录、订单/退款原始事实、发货队列、泛聊天入口 | 没有运营指标 read model、日报、异常 SKU 规则、运营待办；目前的发货队列不视为运营 Agent | 固定近 7 天商品销量、退款率、售后量三个指标，生成异常 SKU 清单 |
| 管理层 | 无独立业务工作流 | 无跨部门固定口径和周报入口 | 在客服、财务、运营 read model 稳定后再做 |

## 7. 当前两周的推进顺序

1. 客服 P0：部署深链、配置测试 Webhook、跑通并记录一次真实升级闭环。
2. 客服 P0.5：基于同一张升级/工单事实表，发送每天一次的值班摘要。
3. 财务 P1：先做只读异常扫描与队列，不改变退款状态。
4. 运营 P2：再做固定指标和异常 SKU 日报，不接物流/仓储。

## 8. 飞书接入策略

第一阶段只使用固定群机器人 Webhook：低权限、无需员工账号映射、不会把飞书变成业务数据库。链接打开本系统后仍使用本项目 JWT/Casbin 鉴权。

后续只有出现明确需求时才增加：

- 飞书卡片回调认领：需要飞书账号与系统员工账号的可信映射；
- 飞书应用待办：需要企业应用权限、回调验签、撤销/状态同步；
- 多群路由：需要值班表和角色归属的真实来源。

在这些前提未满足前，不接入通讯录、文档、多维表格或任意 MCP 写操作。

## 9. 交付纪律

1. 每次只交付一条可观察闭环，不以“Agent 会总结”为完成标准。
2. 写订单、库存、支付、退款的命令必须走确定性应用服务，且有幂等键、审计和失败状态。
3. Agent 的每次执行记录触发原因、使用的事实、调用结果和最终状态；失败必须可重试或进入人工队列。
4. 新 migration 先在独立 `_test` 库验证；不执行 `alembic upgrade head`，生产分支使用明确 revision。
5. 前端页面服务于当前处理入口；不因内部工作流而重构客户侧已可用功能。
