# 电商 AI Agent 交付计划

> 状态：历史交付计划，保留已完成能力和决策背景。当前执行顺序以
> [INTERNAL_AGENT_WORKFLOW_PLAN.md](INTERNAL_AGENT_WORKFLOW_PLAN.md) 为准。

## 1. 产品目标

建设一个可部署、可演示、可持续迭代的电商 AI Agent。Agent 面向客户和内部员工，能够理解业务诉求、读取授权业务数据、调用确定性工具推动业务处理，并在成功、失败、等待或需要人工介入时给出明确结果。

首要业务闭环为：

> 客户提出售后问题 → Agent 查询订单及售后事实 → 自动处理低风险问题 → 回复客户；遇到高风险、异常或信息不足时，升级到对应内部角色。

## 2. 当前产品边界

| 使用对象 | 主要能力 |
| --- | --- |
| 客户 | 浏览商品、咨询商品、购物车、购买、查询订单、查询物流、发起售后 |
| 售后 Agent | 识别诉求、查询订单/支付/物流、处理常见问题、创建或更新售后工单 |
| 客服 Agent | 处理被升级的工单、补充信息、回复客户 |
| 财务 | 审批退款、处理支付失败、回调异常和对账异常 |
| 运营 | 管理商品、库存、售后政策和运营报表 |
| 管理员 | 管理用户、角色、系统配置和审计元数据 |

支付、退款、订单、库存等事实必须由确定性业务服务维护，不能由模型文本直接修改。

## 3. 分阶段交付表

| 阶段 | 目标 | 主要工作 | 完成标准 |
| --- | --- | --- | --- |
| 0. 业务事实统一 | 确定当前系统真正使用的数据来源 | 盘点订单、支付、退款、售后表和服务；确定唯一事实来源；明确 Agent 可读取的数据范围 | 同一业务事实不再由多套表或多条链路分别维护；关键关联关系可从数据库和代码中说明 |
| 1. 售后 Agent 闭环 | 让 Agent 能独立处理常见售后问题 | 接收客户诉求；识别订单/物流/退款意图；调用授权工具；查询事实；回复结果；必要时创建售后工单 | 客户可以通过聊天完成查询和常见售后处理；信息不足、权限不足、风险较高时有明确升级原因 |
| 2. 内部工作台 | 让不同员工角色接管不同类型的任务 | 完善 agent、finance、operator、admin 工作台；实现工单队列、认领、回复、退款待办和异常待办 | 不同角色只能看到和操作授权范围内的资源；升级后的任务可以被员工接收、处理和追踪 |
| 3. 退款业务闭环 | 打通可控的退款流程 | 退款资格校验；客户确认；低风险自动退款；高风险财务审批；支付宝沙箱退款；查询、回调、幂等和失败恢复 | 不重复退款；金额和状态由确定性服务控制；支付成功、失败、未知和异常状态均有可观察结果 |
| 4. 运营自动化 | 处理内部重复性日常工作 | 生成待处理工单摘要、超时任务和支付异常摘要；提供运营报表；为高优先级异常生成内部待办 | Agent 能主动发现和整理内部任务，员工可以按待办处理，不需要手工翻查多处数据 |
| 5. 飞书协作接入 | 将内部任务送达员工日常工作入口 | 选择一个明确场景：工单超时或高风险时，通过飞书发送群通知或创建待办；处理结果回写本系统 | 同一异常不会重复通知；飞书只作为通知和协作出口，业务状态仍以本系统为准 |

## 4. 角色边界

- `agent`：读取和处理自己权限范围内的售后工单，不审批退款，不操作支付资金。
- `finance`：处理退款审批、支付失败、回调异常和对账异常，不修改订单原始事实。
- `operator`：管理商品、库存、政策和报表，不审批退款，不直接操作支付。
- `admin`：管理用户、角色、系统配置和审计元数据，不参与日常售后或退款处理。
- Agent：可以理解诉求、查询事实、调用授权工具和推进低风险流程；不能自行决定金额、绕过权限或用自然语言伪造业务成功。

## 5. 当前不纳入主线的工作

- 不先建设通用 Agent 平台、复杂 Harness 或大规模多租户能力；
- 不新增没有具体业务入口的抽象层、数据表或迁移；
- 不接入物流 MCP，除非当前物流闭环被真实阻塞；
- 不把所有异常简单转给人工，必须给出具体升级原因；
- 不在支付宝沙箱闭环稳定前扩展更多支付渠道；
- 不继续进行与业务闭环无关的大范围前端重构。

## 6. 执行与验收原则

1. 每个阶段先完成一条可手工演示的正常路径，再补当前最危险的失败路径。
2. 涉及订单、库存、支付、退款的写操作必须经过确定性应用服务，并保留审计或执行记录。
3. Agent 的每次关键工具调用都要能追踪触发原因、结果和最终状态。
4. 数据库迁移或已有业务数据写入前，先说明目标库、影响范围和回滚/前滚方式，并取得授权。
5. 未列入本计划的能力暂不进入开发，除非它直接阻塞当前业务闭环。

当前执行顺序以本计划为准；PLAN_V7 及其设计文档作为背景参考，不再要求在核心业务闭环之前完整实施其中所有平台化内容。
