# V7-1A：3C 客服 Agent 升级与飞书值班协作

状态：下一条开发主线。
目标：让 3C 客服 Agent 覆盖售前、交易、履约和售后咨询；低风险问题自主处理，无法可靠处理时，系统主动将明确任务送到值班客服。

## 1. 复用什么，不重造什么

| 现有能力 | 在本流程中的职责 | 是否改造 |
|---|---|---|
| `tickets` / `ticket_messages` | 工单事实、客户追问、AI 和人工回复记录 | 继续作为唯一工单事实来源 |
| `TicketResolutionWorker` | 领取 `AI待处理` 工单、RAG 检索、生成回复或转人工 | 补明确升级原因，不替换 Agent |
| `claim_ticket()` / 客服工作台 | 人工客服认领 `待人工处理` 工单并回复 | 直接复用 |
| JWT + Casbin | 客户归属、客服范围、内部接口授权 | 直接复用 |
| `ToolRegistry` / 现有 MCP 客户端 | 后续挂载受控飞书通知工具 | 不开放任意 MCP 写权限 |

本阶段不新建通用 Harness、任务平台、财务队列或第二套工单系统。飞书也不是工单数据库；它只承接通知和待办。

## 2. 角色与状态衔接

| 主体 | 能做什么 | 明确不能做什么 |
|---|---|---|
| `customer` | 创建工单、查看自己的消息、补充信息 | 查看他人工单、认领、改处理结果 |
| 系统 `TicketResolutionWorker` | 处理无人工认领的 AI 队列，写 AI 回复或升级 | 直接改订单、支付、退款、库存；覆盖已人工认领工单 |
| `agent`（人工客服） | 查看可见队列，认领、回复、关闭自身认领工单 | 查看其他客服已认领的工单；借飞书越权读取客户数据 |
| `operator` | 后续接收脱敏的队列汇总 | 认领客服工单、查看完整客户对话 |
| `admin` | 后续配置值班群和通知开关 | 默认不接收所有客户 PII 或代替客服处理日常工单 |

现有状态保持可用：`AI待处理 → AI处理中 → 已处理`，或 `AI待处理 → AI处理中 → 待人工处理 → 人工处理中/已关闭`。
人工认领后，客户再次追问不得将其重新放回 AI 队列。

## 3. 第一条完整业务流程

```text
1. customer 咨询 3C 商品、交易、履约或售后问题
2. Agent 先读取脱敏问题、知识库资料和已授权的订单/保修事实
3a. 有依据的低风险排查/保修政策问题
    → 给出安全排查和需补充的设备信息
    → status = 已处理或等待客户补充
3b. 危险迹象、确认异常、排查后仍无法解决或无法可靠处理
    → 创建/补充售后工单
    → ticket_messages 写面向客户的升级说明
    → status = 待人工处理
    → 同一事务创建 ticket_human_escalations 记录
4. NotificationWorker 读取待投递 escalation
    → FeishuDutyNotifier 向固定值班群发送脱敏卡片和工作台深链
    → 成功：记录 delivered_at；失败：记录安全错误码、退避重试
5. 人工客服从深链进入内部工作台、登录、认领
    → status = 人工处理中
    → 客服回复或关闭
```

## 4. 必须升级人工的条件

满足任意一项即升级；模型只能建议升级，不能绕过下列确定性规则标记“已处理”。

1. 无可用知识资料，或资料不能支撑客户所问结论；
2. 客户明确要求人工、投诉、争议或情绪激烈；
3. 设备出现冒烟、起火、电池鼓包、漏电等危险迹象，或基础排查后仍无法恢复；
4. 涉及订单/地址/物流修改、支付、退款、金额、赔偿、隐私争议；
5. 模型输出受控的 `[ESCALATE]` 标记；
6. AI 回复后客户再次追问，但没有新的可引用知识。

低风险知识问答（如故障排查、公开保修政策）可由 Agent 直接回复，不需要人工“审核通过”。

## 5. 飞书边界与卡片内容

首版使用一个固定的测试值班群和 `FeishuDutyNotifier`，而不是让模型调用任意群聊、通讯录、文档或表格。

卡片字段仅限：工单号、紧急度、升级原因码、脱敏问题摘要、创建时间、内部工作台链接。禁止写入姓名、手机号、邮箱、完整订单号、支付信息、退款信息、完整消息历史和原始模型异常。

点击卡片只打开工作台链接。认领动作仍在本项目 API 内完成，身份以本项目 JWT/Casbin 为准；首版不做飞书回调认领和飞书账号映射。

## 6. 去重、重试与人工兜底

新增的 `ticket_human_escalations` 每张工单每一代升级最多一条活跃记录，幂等键为 `ticket_id + escalation_generation`。

- 飞书投递成功只代表消息送达，不改变工单业务状态；
- 投递失败时状态仍为 `待人工处理`，内部工作台队列始终可见；
- 失败记录只保留安全错误码，不保存飞书响应正文或客户正文；
- 客户在未认领前补充新信息后，Agent 可以再次处理；若再次升级则创建下一代通知；
- 已认领/关闭的工单不再发送新的升级通知。

## 7. 明天的实现切片

### A. 现有 Agent 升级语义

补齐升级原因枚举和测试：无知识、明确人工、交易/资金事项、模型升级、重复追问。验证 Agent 回复、升级说明和人工认领不会相互覆盖。此切片不需要迁移。

### B. 应用内升级投递记录

新增 `ticket_human_escalations`，只记录工单引用、原因码、投递状态、尝试次数、时间和安全错误码。升级状态与记录在一个事务中写入。先写 migration 与测试；执行开发数据库迁移前单独确认。

### C. 飞书通知适配器

新增最小 `FeishuDutyNotifier`：从配置读取测试群/Webhook 或应用凭证，只能发送固定结构卡片。增加可替换 fake notifier 的测试。开发期默认关闭，未配置飞书时不阻塞工单升级。

### D. 通知 worker 与演示入口

启动一个轻量后台 worker 投递待发通知；在客服工作台显示“已通知/待重试”但不暴露飞书原始异常。完成客户建单、Agent 升级、飞书通知、客服认领回复的一次端到端演示。

### E. 每日值班摘要

复用 C/D 的通知能力：每天固定时间扫描待人工、高优先级、超时未认领工单，向同一群发送一条脱敏摘要。首版不创建新的报表平台或多维表格同步。

## 8. 逐切片验收

| 切片 | 最小验收 |
|---|---|
| A | 低风险知识问题自动回复；五类升级条件均转人工；已认领工单不被 AI 改写 |
| B | 重复处理不生成重复升级记录；升级状态与记录要么一起提交、要么一起回滚 |
| C | 固定卡片字段正确；缺飞书配置时工单仍进入人工队列；不含 PII |
| D | 测试群收到一条通知；客服可从链接认领并回复；飞书失败后可重试且不丢单 |
| E | 定时摘要只包含当前仍需人工的工单，重复执行不刷屏 |

## 9. 后续而非前置

运营日报、发货催办、退款/支付异常摘要都可以复用通知 worker，但要等各自确定性 read model 成熟后再接入。
当前 Casbin 尚无 `finance` 角色，因此不提前实现财务 Agent、财务通知或资金操作。
