# JDDC 3C 客服会话：200 条真实问题抽查

> 审查日期：2026-08-27。目的不是把公开语料的客服回复当作本项目答案，而是从客户真实表达中识别
> “客户究竟想让系统完成什么”。

## 样本与限制

- 来源：本机 JDDC 基线脱敏会话的 3C 会话候选集，共 3,316 条（每个会话选一条可行动用户消息，并保留
  最近上下文）。
- 抽样：固定随机种子 `20260827`，按现有弱主题分层随机抽 200 条：设备问题 25、售前/价保/安装 25、
  人工/投诉 20、售后过程 30、退货退款 30、物流配送 25、订单/支付/发票 25、其余 20。
- 现有弱主题只用于分层，不是人工标注；一个会话可能有多个主题。会话级 3C 过滤也会保留少量非 3C 商品
  原话，因此以下结论只抽取可迁移的对话与流程模式，最终功能范围仍是 3C 数码商品。

## 从 200 条真实表达得到的第一性原理

客户不会把自己归类成“物流意图”或“退款意图”。他们要的是一个结果：收到货、改约、拿到退款、
撤销错误申请、修好设备、确认是否能换，或者确认有人接手。客服 Agent 的职责是把这一个结果推进到
**真实状态已核验、下一步明确、动作已完成或正确交接**。

因此，判断 Agent 是否解决问题的最小单位不是“回答一句话”，而是下面的状态变化：

```text
未知/混乱
  → 客户目标被确认
  → 对应订单、商品、售后对象被定位
  → 必要业务事实被核验
  → 给出可执行下一步或客户选择
  → [需要时] 已确认的确定性命令执行并核验
  → 完成 / 等待客户 / 等待员工 / 明确失败
```

## 真实案例与客户的实际诉求

### A. 客户并不总是在“查物流”，很多是在协调履约

| JDDC ID | 原话（含上下文要点） | 实际目标 | 正确下一步 |
|---|---|---|---|
| `809d…-4` | “我的今天无法到达，我自己过去拿”“明天离开深圳，没办法签收” | 在离开前拿到货或改变交付方式 | 查物流节点、网点/自提资格、可改约时间；展示官方联系入口，不给私人电话 |
| `1cf5…-1` | “麻烦调整一下配送电话，原电话因手机出现故障” | 保证配送可联系，而不是修手机 | 定位待配送订单 → 校验可修改字段 → 让客户确认新联系方案 |
| `eae1…-3` | “东西没有收到”“显示签收了” | 处理签收异常 | 查签收、配送、收件证明和异常规则；不是普通 ETA，也不能宣称丢件 |
| `b8f7…-0` | “这个订单下单…天了都没有物流进度更新?” | 确认停滞原因和补救路径 | 查付款、发货、物流节点、承诺时间；超时才给催件/取消/人工选项 |
| `59d6…-1` | “修改配送时间” | 改约 | 需要活动订单和可用时段；客户选择后才调用履约命令 |

**结论**：物流不是一个工具名 `track_order`。至少要区分预计送达、未发货、运输停滞、签收异常、
改约、改联系信息、网点自提、少件。它们共享订单/履约事实，但后续策略完全不同。

### B. “退款/退货”往往描述的是已经走到一半的售后状态

| JDDC ID | 原话（含上下文要点） | 实际目标 | 正确下一步 |
|---|---|---|---|
| `c8b3…-4` | “我退货的单子不想退了” | 撤销进行中的退货 | 查退货是否已取件/入库/退款；仅在可撤销时向客户确认撤销 |
| `1259…-4` | “昨天申请退货后今天想取消…取消后能申请换货吗” | 先撤销退货，再改换货 | 两个连续状态转换；先查原申请阶段，不能把两步合成“重新申请” |
| `9d33…-1` | 两个商品只退一个，取件员把合并发票也拿走 | 退货和发票关联是否正确 | 查订单行、售后行、取件清单和发票状态；这是事实冲突，不是普通退货入口 |
| `d469…-3` | 两个引闪器均被取走，“退款只给我退了一个的钱” | 核对金额差异 | 查取件数量、售后商品行、退款金额与审核；确认差异后才升级财务/客服 |
| `0e84…-0` | 商家已收到货，但售后期过了，请帮申请退款 | 用已发生的收货事实解决超期退款 | 核验退货物流、商家收货、售后关闭原因；规则例外需完整证据升级 |

**结论**：第一次说“我要退货”才适合引导自助入口。客户提到“申请过、取走、审核、到账、取消、
改成、超期、少退”时，系统必须进入 `get_after_sale_facts / get_refund_facts`，而不是再次贴退款链接
或直接开空工单。

### C. 状态转换是高价值的客服工作，不是单个意图

| JDDC ID | 原话 | 实际目标 | Workflow 关键问题 |
|---|---|---|---|
| `7700…-5` | “我的电磁炉退货现在修改换货” | 退货改换货 | 原退货是否可撤销？商品是否在库？客户确认换货型号吗？ |
| `ad16…-0` | “大了要换货，怎么操作不了，只能退款呀?” | 找出换货入口缺失原因 | 订单是否符合换货条件？是否只有退款资格？ |
| `4733…-1` | 电脑出问题，昨天申请返修，“现在不想要了，能退货不” | 返修改退货 | 维修是否已受理/寄出？退货资格和设备状态如何？ |
| `2b26…-2` | 主板换货中，发现 CPU 不兼容，想退货另买 | 换货改退货 + 推荐兼容商品 | 售后状态转换和兼容性查询是两个关联请求，不能混为一个动作 |

**结论**：这些案例反驳了“一个句子只有一个 intent”。应保存请求栈：主请求、附属请求、对象和依赖；
先完成共有事实查询，再请客户做一次明确选择。任何取消、换货、退款等命令都必须由确定性服务二次校验。

### D. 设备问题的客户目标是“恢复使用”，不是马上拿到工单号

| JDDC ID | 原话 | 实际目标 | 正确下一步 |
|---|---|---|---|
| `b329…-11` | 阅读器更新到没电后无法启动 | 尽快恢复设备 | 核对型号/保修，给安全的恢复/充电/重置步骤，记录尝试结果；失败再引导维修 |
| `704c…-4` | 路由器插电没反应 | 判断供电、设备故障或保修 | 先安全排查电源/适配器；查订单和保修；不应只回答“申请售后” |
| `3144…-4` | 两条数据线都显示充电但电量反而下降 | 判断使用环境、线材或设备问题 | 记录设备/充电头/接口、交叉测试；必要时申请单件售后 |
| `8c7c…-9` | 硬盘无法识别，技术建议联系商家更换 | 基于已有技术结论办理换货 | 查订单和售后资格，确认只寄故障盘还是整套，提出换货命令前确认 |
| `975e…-1` | 点读笔进水后不能开机 | 安全处理和有偿/保修维修边界 | 先停止通电和充电，说明进水边界；查保修并转维修而非继续普通排查 |

**结论**：设备流程要保存 `symptom`、`safety_risk`、`attempted_steps`、`device_model`、`warranty_facts`。
没有这些状态，客户说“还是不行”时 Agent 只能从头再问；安全风险（进水、鼓包、冒烟）必须绕过普通排查。

### E. 售前、安装、价保和发票不是纯知识问答

| JDDC ID | 原话 | 实际目标 | 所需事实 |
|---|---|---|---|
| `9a1f…-1` | “这个订单要申请价格保护” | 提交或查询价保 | 订单、商品、购买时间、当前政策和价格证据 |
| `8164…-4` | 降价后已退贵价商品并重买，“目前没有收到款” | 同时追踪退款与新订单 | 两个订单、退款状态；不能只讲价保政策 |
| `9b6c…-3` | 下单时忘记加服务，“能补一个安装服务吗” | 给既有订单补安装 | 商品是否支持、订单是否已发货、服务是否可加购 |
| `807f…-2` | “发票单位名我填错了” | 更正/重开发票 | 发票是否已开、抬头类型、订单状态与可操作范围 |
| `68e7…-0` | “能开增值专用发票吗? 上次开的是普通发票” | 判断重开资格 | 当前发票状态、购买主体、专票资质与政策 |

**结论**：RAG 可以解释规则，不能判断“这笔订单是否已经开票/是否在价保期/能否补安装”。此类问题通常是
`policy + order fact` 的混合请求，先查事实，再引用政策。

### F. 短句、元数据和“人工”本身不是无意义噪声

200 条中反复出现三种极短输入：订单元数据（例如“订单编号…订单金额…”）、续接短句（“我发货了”、
“我的退货单”、"没有"）和人工入口（“人工”“客服”“是真人客服么”）。它们说明：

1. **订单号不是诉求。** 有订单号但没有问题时，应从上下文恢复当前请求；没有当前请求则只问一个问题：
   “我已找到该订单，您想查配送、退款、售后还是发票？”
2. **短句必须优先解释为对 pending question 的回答。** `“没有”`、`“可以”`、`“第一个”` 脱离当前
   Case 无法可靠分类，不能降级成泛 RAG。
3. **人工是一种渠道选择，不是业务原因。** 客户明确选择人工可转交；仅问“是真人吗”应先解释能力并收集
   一句问题摘要。交接摘要必须包含现有事实，而不是只保存“人工”。

## 直接否定的五个旧假设

1. “出现退款词就给退款链接”：错误；很多客户已在退款、取件、审核或到账阶段。
2. “出现人工词就建工单”：错误；大量只是询问渠道或错过回电。
3. “物流都调用 `track_order`”：不够；履约协调至少需要读取、选择、受控修改和异常升级。
4. “故障问题只走知识库”：不够；排查、保修、维修、换货和危险情形有不同边界。
5. “会话历史足以承接短句”：不够；系统需要显式保存当前对象、已核验事实和待客户回答的问题。

## 对工作流的最小实现要求

为了让 Agent 解决上述真实问题，而不是更会解释，首批 Support Case 必须能保存和推进：

```text
主请求 / 附属请求
关联订单、商品、售后申请
客户声称与服务端核验事实（严格分开）
待客户选择或待补字段
待执行命令和确认幂等键
当前状态：处理中 / 等客户 / 等员工 / 已完成 / 已失败
追加式事实、选择、命令和失败事件
```

首批共享只读能力的优先顺序应是：

1. 本人候选订单、订单行和履约节点；
2. 本人售后申请、取件/维修/换货状态；
3. 本人退款申请、金额、审核和到账状态；
4. 发票、价保、安装和配送选项的订单关联事实；
5. 3C 型号、兼容性、保修与安全排查知识。

在这些读取能力存在前，不开放聊天 Agent 对取消订单、改地址、撤销售后、换货、退款等写操作的自治执行。
客户确认后的每个命令仍必须由确定性服务做权限、状态、金额、幂等和审计校验。
