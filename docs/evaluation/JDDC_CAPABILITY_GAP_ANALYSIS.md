# JDDC 真实客服语料：能力缺口分析

> 版本：2026-08-27。本文用于决定客服 Agent 下一批业务能力，不把 JDDC 原始标签改名为本项目金标。

## 1. 分析范围和口径

分析对象是本机 JDDC 基线脱敏数据中包含 3C 商品线索的 3,316 个会话。原始数据没有提交到仓库，
分析从 `/tmp/jddc_baseline.zip` 读取；仓库中的 `/tmp/jddc-3c-provisional.jsonl` 是每个会话抽取一条
可行动用户消息的复核副本。

- 3C 会话：3,316 个；用户消息：32,222 条；客服消息：40,914 条。
- 每个 3C 会话至少有 6 条消息，中位数 20 条，平均 22.1 条，90 分位 35 条，最长 78 条。
- 用户消息中 10,151 条不超过 4 个字符，18,265 条不超过 8 个字符；“好的”“是的”“这个”“之前的”
  等短句和订单号/脱敏字段非常常见。
- 在所有用户消息上用探索性词面规则统计，约 62.2% 的会话出现两个及以上业务类别，约 22.4% 出现三个
 及以上类别。该统计用于发现候选缺口，不是人工标注准确率。

以下数量允许重叠：同一条消息可以同时包含订单、物流和退货诉求。

## 2. 结论：当前最大问题不是“模型不懂”，而是业务承接不足

当前路由已经能区分 RAG、普通 Agent、配机和一部分退款/设备排查，但真实会话显示有四个结构性
缺口：

1. **实时业务路由仍然过粗。** `order`、`after_sales`、`refund`、`logistics` 下面混合了查询、异常、
   修改和状态转换；例如“查询物流”和“已签收但没收到”不能走同一个回答路径。
2. **缺少只读事实工具。** 发票、价保、配送约束、退货物流、退款状态和部分售后事实无法核验，模型只能
   解释政策或让客户重复描述。
3. **缺少受控写操作和确认节点。** 用户频繁要求取消订单、改地址/手机号、取消退货、换货改退货、
   补发缺件，但现有聊天 Agent 没有对应的确定性命令入口，不能安全推进闭环。
4. **多轮状态和指代是主路径，不是边角场景。** 大量短句是在上一轮回答基础上的确认、否定、补充或纠正；
   仅按当前一句分类必然把“这个”“之前的”“是的”路由错。

当前 JDDC 3C 会话里每个会话本身就有较长上下文；因此“把复杂问题交给 Workflow”是必要的，但 Workflow
必须携带业务状态、已核验事实和待用户选择，不能只是再调用一次通用 AgentLoop。

具体的真实话术、客服判断和由此反推的状态字段见
[客服工作流推导演练](JDDC_CUSTOMER_SERVICE_DESIGN_WALKTHROUGHS.md)。

另外，[200 条分层真实问题抽查](JDDC_200_CASE_AUDIT.md)验证了这些结论：真实客户多在描述
流程中间状态、履约协调或事实冲突，不能用“退款/保修/人工”单关键词直接决定下一步。

## 3. 当前项目与语料的对照

### 已有且可复用

- RAG/知识库、商品搜索和对比、库存查询、本人订单/物流查询、支付状态查询、售后工单查询。
- 配机 Plan-and-Execute 与最近加入的 SupportWorkflow 路由骨架。
- JWT/Casbin、客户资源归属、工单认领/回复/关闭、退款确定性服务和支付宝沙箱状态机。

### 部分覆盖但不能宣称闭环

- `track_order` 能查订单，但不能区分“预计送达”“物流停滞”“已签收未收到”“配送备注/改约”。
- `check_after_sales` 目前主要面向工单状态；JDDC 中的换货、取件、运单、检测、维修和取消售后属于另一套
  售后申请状态，不能只返回一个工单号。
- 退款页面和退款服务已存在，但聊天 Agent 没有统一的退款事实读取/候选订单选择/确认节点。
- 设备故障已有排查知识，但“排查失败后报修”“保修资格”“跨地区维修”“缺发票/保修卡”还没有事实工具。
- 支付 API、发票、价保和运营履约接口存在一部分后端能力，但尚未以最小授权工具接入客服工作流。

### 明确缺口

#### A. 路由和会话状态

建议把当前粗粒度路由扩展为 `domain + operation + state + next_step`，至少覆盖：

`order_lookup`、`delivery_track`、`delivery_exception`、`delivery_instruction`、`order_cancel`、
`order_modify`、`payment_status`、`invoice`、`price_protection`、`refund_request`、`refund_status`、
`return_logistics`、`after_sales_status`、`after_sales_transition`、`repair_warranty`、
`device_troubleshooting`、`product_compatibility`、`human_contact`。

每轮还要保存：候选订单/商品、已确认事实、未决问题、待客户选择、下一允许动作和事实截止时间。

#### B. 只读工具（优先于写工具）

按业务价值建议依次补：

1. `list_recent_orders`/`get_order_facts`：展示候选订单和订单商品，让“最近那单”不必强行索要订单号；
2. `get_delivery_facts`：物流节点、承诺时间、签收状态、配送方式和异常原因；
3. `get_after_sale_facts`：售后申请类型、状态、检测/取件/运单/退款关联状态；
4. `get_refund_facts`：退款申请、审批、处理中、成功、失败和金额校验；
5. `get_invoice_facts`、`get_price_protection_facts`：发票和价保查询；
6. `get_delivery_options`：配送范围、预约时段、自提/快递柜和可否修改备注。

每个工具必须根据服务端用户身份过滤资源，返回结构化事实和 `not_found/unsupported/unavailable`，不能
让模型从空结果推断成功。

#### C. 多步骤工作流

- **换货改退货：** 查询售后申请 → 确认是否已寄出/检测 → 向客户复述理解 → 客户确认退货或继续换货 →
  只有确定性命令允许时才执行；否则转售后人工。
- **部分缺货：** 查询订单商品和库存 → 明确哪些商品可发/缺货 → 让客户选择等待、部分发货或取消缺货项 →
  对不可逆动作再次确认。
- **签收异常/取件失败：** 查询物流和售后取件状态 → 区分未取件、已取件、运单无效、已签收未收到 →
  根据责任边界给出下一步或升级。
- **设备故障到报修：** RAG 排查 → 询问关键事实 → 判断是否危险/仍未解决 → 申请售后或创建人工任务。

这些不是一个关键词对应一个答案，而是可暂停、等待客户选择、恢复和失败升级的状态机。当前新增的
`SupportWorkflowAgent` 只是并列编排入口；持久化 checkpoint、`interrupt/resume` 和真正的事实节点应在
第一条多步骤业务闭环中补齐。

#### D. 知识库和客服体验

知识库至少补齐：退换货条件与时限、换货/退货转换、取件和邮费、发票、价保、配送区域/时段、自提/快递柜、
安装与跨地区维修、不同品牌保修边界。每篇资料要有来源、适用商品/渠道、有效期和“不能据此判断”的边界。

前端应支持候选订单卡片、最多三个业务选项、确认/取消、当前步骤和“等待客户/等待人工”状态；不要让用户
只能通过工单号反查，也不要把“客服”三个字一律解释成创建工单。

## 4. 推荐开发顺序

这里的“第一优先级”是共用的事实读取、状态和确认能力，不是只选择换货改退货这一种业务。换货改退货、
部分缺货、签收异常都只是用来验收同一套多步骤机制的代表案例。

1. **客服多意图骨架。** 将 `domain + operation + state + next_step` 接入普通聊天和 SupportWorkflow；
   统一保存当前诉求、已核验事实、待确认问题、候选订单/商品和失败原因。简单问题仍快速走 RAG/AgentLoop，
   多主题或状态转换才进入工作流。
2. **订单/物流主线。** 补订单候选、物流节点、承诺时间、签收异常、配送备注/自提等只读事实；这是会话覆盖面
   最大的一组，共同服务“查单”“什么时候到”“没收到”“地址/电话/配送约束”等多个意图。
3. **退换货/售后主线。** 补售后申请、换货/退货转换、取件/运单、检测和保修事实；用换货改退货、部分缺货、
   取件失败三个场景验证“先核验、再复述、再选择/升级”。当前先不接不可逆写操作。
4. **支付、退款、发票、价保主线。** 读取先行，写操作继续走现有确定性服务；禁止 Agent 只凭文本改变金额、
   付款、退款、发票或价保状态。
5. **设备和商品主线。** 继续补品牌/型号兼容、安装、故障排查、保修资格和排查失败升级；知识不足时返回明确
   的“不确定/需要人工”，不能用普通 RAG 文案代替事实。
6. **多轮状态持久化。** 对“已询问/等待选择/已确认/执行失败/需人工”落库或使用可靠 checkpoint，重启后能
   恢复；有了状态后再逐个增加取消订单、改地址、取消售后、部分发货等写命令，每个命令单独设计幂等键、权限、
   审计和失败状态。
7. **内部协作。** 把已完成的事实和异常汇总给客服、财务和运营。JDDC 本身不能证明员工工作流需求，但上述异常
   事件天然适合进入人工队列、班前摘要和后续飞书通知。

## 5. 不应直接做的事情

- 不把 JDDC 的客服回复或 `is_transfer` 当作本项目动作金标；它们不包含订单事实、权限和金额结果。
- 不因“人工”“客服在吗”就直接创建工单；先判断是联系方式、平台/商家归属还是明确要求人工处理。
- 不因为“退货/换货”关键词就直接退款、取消或改订单；先查事实、复述理解并等待客户确认。
- 不把一次全量规则扫描的 0 违规当成意图准确率；动作准确率需要盲审金标和真实工具轨迹。
