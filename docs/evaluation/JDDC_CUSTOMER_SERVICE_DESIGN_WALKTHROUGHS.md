# 从真实客服对话反推 3C Agent 工作流

> 版本：2026-08-27。本文用 JDDC 脱敏会话中出现过的表达方式推导产品行为；商品、订单、时限和政策
> 仅为说明工作流，不能被当作本项目真实业务事实或自动执行依据。

## 结论先行

客服 Agent 的核心职责不是给每句话分类，而是把客户混乱、缺省、可能互相矛盾的表达整理成一个
**可核验、可继续、可审计的服务请求**。

一条服务请求至少应有：

```text
客户目标 + 关联对象 + 已知事实 + 未知/冲突事实 + 当前阶段 + 下一步 + 允许的动作
```

例如，“上午申请换货，现在发现 CPU 不兼容，想退货另买”不是 `refund` 一个意图，而是：

```text
目标：把进行中的换货改成退货退款
对象：本人那笔主板订单及其售后申请
已知：客户称已申请换货；原因为兼容性不满足
未知：对应订单、换货是否已发出/签收、售后是否允许撤销
下一步：查询订单、售后状态、商品兼容资料
允许动作：只读查询；向客户展示可选方案；客户确认后才提交确定性售后命令
```

LLM 应负责理解自然语言、提取候选请求、把核验事实组织成自然的追问；它**不能**自行判定订单状态、
金额、资格或直接写入订单。业务服务负责事实和写操作；Workflow 负责把中断、选择、恢复、失败和转人工
串起来。

## 真实表达的客服推理演练

下面每例都不是“唯一标准话术”。重点是：为什么此时不能直接回答、直接建单或直接执行。

### 1. 最近订单何时派送：先查事实，不能凭经验承诺

**客户原话（JDDC 风格）**：

> 我待会要出去，可是手机坏了，请问什么时候订单派送

**合格客服答复**：

> 我先帮您查正在配送的手机订单和今天的配送状态。如果有多个待收货订单，我会列出来请您确认；
> 查到后会告诉您当前物流节点、预计送达时间和可用的官方联系/改约入口，不会直接提供配送员私人号码。

**为何这样做**：客户表面问“什么时候”，实际可能还需要改约或联系配送。预计时间、配送方式和是否可以
改约都是订单事实，不能由 RAG 或模型猜测。手机号损坏解释了紧急性，但不改变配送规则。

**需要的状态与工具**：`delivery_track`；`selected_order` 为空时先 `list_recent_orders`，否则
`get_delivery_facts`；如果客户选择改约，再进入 `delivery_instruction`，而不是在本轮改地址。

### 2. 已下单却未发货：先区分正常等待、缺货、异常和取消意愿

**客户原话**：

> 客服，我昨天下的订单为什么现在还没发货

**合格客服答复**：

> 我来核对这笔订单的付款、备货和承诺发货时间。若仍在承诺时间内，我会说明当前进度；若缺货或已超时，
> 我会把可选处理方式列给您确认，例如继续等待、取消未发货商品，或在订单支持时先发有货商品。

**为何这样做**：`未发货` 不等于异常，也不等于客户要退款。客服必须先读取订单承诺和商品行状态；取消、
部分发货等都是不同的不可逆命令，必须由客户在事实明确后选择。

**需要的状态与工具**：`order_fulfillment / delayed_dispatch`；
`get_order_facts → get_delivery_facts → get_stock_facts（仅缺货时） → ASK_CHOICE`。

### 3. 一个订单两件商品，一件缺货：客户常常还没有提出最终请求

**客户原话**：

> 尖子生那本还没货，说还得几天；北师大数学全解有货。

**合格客服答复**：

> 我理解您这一单里《尖子生》暂时缺货，而《数学全解》有货。我先核对订单和预计到货时间。
> 确认后您可以选择：继续等待整单、先发有货商品，或取消缺货商品；若想换成其他商品，也可以先告诉我
> 目标商品，我再核对库存和差价。这样理解对吗？

**为何这样做**：客户是在陈述事实，并未明确要求拆单、取消还是换货。优秀客服会把隐含选择显性化，
但不假定客户要哪一个。这里“复述理解 + 最多三个可行动选项”比无限追问更友好。

**需要的状态与工具**：一个请求可包含 `delivery_delay` 和 `partial_fulfillment` 两个 operation；
保存 `order_id`、`affected_line_items`、`available_options`，等待客户选择。

### 4. 首次退货：给入口是快速路径，但仍要能承接失败

**客户原话**：

> 这个订单里东西有质量问题，可以申请退货吗

**合格客服答复**：

> 可以。我先核对这笔订单是否已签收、商品是否在售后期限内；符合条件的话，您可以在订单详情中选择
> “申请售后”并填写质量问题。若页面没有入口、申请被拒或商品已寄回但无法提交，请把页面提示发我，
> 我会继续查该笔售后状态。

**为何这样做**：首次申请通常适合自助入口，不能因出现“质量问题”就建工单；但也不能只贴链接后丢失上下文。
客户下一句“已经退了”应匹配这次售后申请，进入状态查询，而非再建一次工单。

**需要的状态与工具**：`refund_request`；先 `get_order_facts` + `get_after_sale_eligibility`；
保存 `offered_self_service=true` 和候选订单，而不是用关键词猜“之前是否已引导”。

### 5. 退款未到账：读退款事实后才能判断异常

**客户原话**：

> 我前几天退了，到现在还没收到退款。

**合格客服答复**：

> 我先查询这笔售后是否已收货、审核是否完成，以及退款当前是处理中、成功还是失败。不同支付方式的到账
> 时间不同；如果系统显示已超出承诺时间、退款失败或金额不一致，我会把已核验的订单和异常原因提交给人工处理。

**为何这样做**：`前几天` 不是“超时”的业务证据。先读退款状态能避免客户重复申请、重复退款，也让人工收到
完整事实而不是最后一句“没到账”。

**需要的状态与工具**：`refund_status`；`get_refund_facts → policy_check(expected_arrival) → ANSWER / ESCALATE`。

### 6. 已申请退货但没有上门取件：异常不等于立刻建单

**客户原话**：

> 我申请售后，为何一直要求自己送到自提点，上门取货取消了？

**合格客服答复**：

> 我先核对这笔售后当前的取件方式、取消原因和您所在地区可用的取件选项。若系统仍支持重新预约，
> 我会给您可选时间；若没有可用的上门取件且政策与订单条件不一致，我会携带订单、售后和配送事实升级处理。

**为何这样做**：客户提出的是“取件方案为什么变了”，可能是区域覆盖、爽约、商品属性或系统异常。
在未查事实前建单只会制造信息不全的工单；查不到、规则冲突或没有可执行替代方案才升级。

**需要的状态与工具**：`return_logistics / pickup_exception`；
`get_after_sale_facts → get_delivery_options → policy_check → offer_rebook | escalate`。

### 7. 进行中的换货要改退货：状态转换，不是普通退款

**客户原话**：

> 上午我申请了换货，但华擎说这块主板不能用我的 CPU，所以想退货另外买能用的。

**合格客服答复**：

> 我理解您希望把这笔主板的换货申请改为退货退款，原因是与现有 CPU 不兼容；同时您可能还需要确认
> 可兼容的主板型号。我会先核对原换货是否已经发出、售后当前阶段和订单商品。若换货尚未进入不可撤销
> 阶段，我会向您确认“撤销换货并改为退货退款”；若已发出或正在检测，我会说明可行路径并转售后专员处理。

**为何这样做**：一个用户消息有两个目标：售后状态转换 + 选购兼容商品。两者应共享商品事实，但不能把“推荐”
误当成“改售后已经成功”。这里可先完成信息查询，客户确认后再由确定性服务发命令。

**需要的状态与工具**：子流程 `after_sales_transition` 与 `product_compatibility`；
`get_after_sale_facts + get_order_facts + search_component → ASK_CONFIRMATION → transition_after_sale`。

### 8. 故障耳机：先安全排查，失败后保修，而不是一开始就强制转人工

**客户原话**：

> 两只耳机不能同时戴，隔着脑袋就信号不好，刚收到就这样。

**合格客服答复**：

> 我理解为两只耳机都能充电，但左右耳同时佩戴时连接不稳定。为避免误判，我先帮您核对型号和订单保修，
> 再请您依次尝试：断开蓝牙后把两只耳机放回盒内重置、分别重新配对、在另一台手机上短暂测试。
> 如果仍不能同时稳定连接，我会基于订单状态为您发起检测/换新或报修的下一步，不需要您重复描述问题。

**为何这样做**：故障症状可以由 RAG 提供排查步骤，但保修资格、购买时间和处理方式必须是订单事实。
最重要的是把“已做过哪些排查”存下来，避免客户每次都重新开始。电池鼓包、冒烟等安全风险则应跳过排查，
直接提示断电并走高优先级人工。

**需要的状态与工具**：`device_troubleshooting`；`get_order_facts → retrieve_safe_guide → collect(troubleshooting_steps)`
→ `get_warranty_facts → offer_after_sale / escalate`。

### 9. 购买前的兼容性：事实不足时确认部件，不要给概率性承诺

**客户原话**：

> 这个主板能用我的 CPU 吗？

**合格客服答复**：

> 可以帮您核对。请把主板和 CPU 的完整型号发我，或从商品页选择对应商品；我会比对插槽、芯片组、
> BIOS 支持和内存规格。信息不足时我不会直接说“能用”，因为同系列型号的接口和 BIOS 版本可能不同。

**为何这样做**：这不是售后，也不是库存查询；它需要规范化商品实体和可信规格来源。澄清是为了把一个可能
造成购买损失的模糊问题变成可验证问题，不是推给人工。

**需要的状态与工具**：`product_compatibility`；`resolve_product_entities → search_component / trusted_spec` →
`ASK_CLARIFICATION | ANSWER`。若客户已购买且确实不兼容，再将该事实传给售后子流程。

### 10. 发票与换货并存：同一轮可有两个关联但不同的任务

**客户原话**：

> 发票现在下载，还是等换货完再下载？

**合格客服答复**：

> 我先确认这笔订单的换货状态和发票是否已经开具。若换货会改变商品或金额，我会说明现在下载的发票
> 是否需要后续重开；如果发票已开且不受本次换货影响，可直接下载。您不需要因为问发票而重新创建售后。

**为何这样做**：这不是单纯 FAQ。政策说明可以来自知识库，但“该订单已经开票了吗、换货会否影响金额”必须
通过订单和发票事实核验。

**需要的状态与工具**：`invoice` + `after_sales_status`；
`get_invoice_facts + get_after_sale_facts → policy_check → ANSWER`。

### 11. “人工服务？”：澄清人工的含义，而不是偷换成创建工单

**客户原话**：

> 人工服务？？

**合格客服答复**：

> 我是智能客服，可以先帮您查订单、物流、售后或商品问题。您是希望转人工，还是先告诉我遇到的具体问题，
> 我优先帮您处理？

**为何这样做**：可能是在找联系方式，也可能是不满意或有紧急异常。没有问题摘要就建单，会让客服只看到
“人工服务”，也无法提高解决率；但客户明确选择人工后应尊重选择并带上已收集的事实转交。

**需要的状态与工具**：会话级通用 `human_handoff`；保存 `handoff_requested=true`，优先收集一个问题摘要，
而不是将“人工”作为业务原因。

## 由这些案例得到的工作流模型

### 1. 不是单意图路由，而是“服务请求栈”

一条消息最多提取三个按先后依赖排序的请求：

```json
{
  "requests": [
    {
      "domain": "after_sales",
      "operation": "transition",
      "desired_outcome": "exchange_to_return",
      "subject_refs": ["current_order", "current_after_sale"],
      "customer_claims": ["exchange_already_submitted", "cpu_incompatible"],
      "missing_facts": ["after_sale_stage"],
      "risk": "controlled_write"
    },
    {
      "domain": "product",
      "operation": "compatibility",
      "desired_outcome": "find_compatible_board",
      "subject_refs": ["current_cpu", "replacement_board"],
      "risk": "read_only"
    }
  ]
}
```

这是一份 LLM 的**候选理解**，必须经过 schema、当前会话状态和业务工具结果校验。最多三个请求是为了
避免一段聊天被无限拆解；超过时先处理客户明确的主目标并说明其余事项。

### 2. 每个请求都走同一组稳定阶段

```text
理解/提取
  → 定位主体（本人候选订单、商品、售后申请）
  → 读取必要事实
  → 规则与资格判断
  → 回答 / 澄清 / 展示选择 / 等待确认 / 升级人工
  → [仅确认后的允许命令] 执行
  → 再读一次事实核验结果
  → 完成、失败或转交
```

`RAG` 只在“政策、操作步骤、排查指南、可信规格”阶段提供依据；它不能代替订单、物流、退款、发票或
售后事实。简单 FAQ 可直接结束在 RAG；实时查询和任何状态变更必须进入后续阶段。

### 3. `pending` 不是历史文本，而是可恢复的业务状态

每个会话最多保留一个活跃主请求（以及零到两个附属请求），字段最小化为：

| 字段 | 例子 | 用途 |
|---|---|---|
| `case_id` / `session_id` | 当前聊天会话 | 权属和恢复游标 |
| `request_stack` | 换货改退货 + 兼容性 | 多意图顺序 |
| `selected_subjects` | 订单、商品、售后申请 ID | 避免“最近那单”歧义 |
| `verified_facts` | 售后未发货、退款处理中 | 只保存服务端事实及时间 |
| `pending_question` | 请选择等待/部分发货/取消 | 让“是的”“这个”有明确语义 |
| `pending_command` | `cancel_after_sale` | 命令、参数摘要、过期时间、幂等键 |
| `status` | `awaiting_customer` / `awaiting_staff` | 恢复、超时、前端展示 |
| `audit_events` | 读取、选择、执行、失败 | 给客户、客服和评测追溯 |

客户回答“第 2 个”“可以”“不是这个订单”时，优先由 `pending_question` 解析；没有 pending state 才把它
当普通新问题。这样不会依赖模型从几十轮历史里猜指代。

### 4. 三种暂停必须明确区分

| 暂停对象 | 例子 | 恢复输入 | 是否可执行写操作 |
|---|---|---|---|
| 等客户补信息 | “哪个订单？” | 订单选择/型号 | 否 |
| 等客户确认 | “确认撤销换货并申请退货吗？” | 明确确认 | 仅调用已审计的确定性命令 |
| 等员工判断 | 超额退款、规则冲突、物流丢件争议 | 客服/财务决定 | 员工审批后才可能执行 |

这就是 LangGraph `interrupt + persistent checkpointer + thread_id` 应承担的职责；它不是“又调用一次模型”。
节点在 interrupt 前不得发生不可幂等的写入，恢复时必须通过同一个幂等键再次校验事实。

### 5. 借鉴成熟产品，但不引入额外平台

- 借鉴 **Rasa Flows**：LLM 可以理解口语，但每个业务流明确声明所需客户信息、所需 API 事实和分支；
  将“订单选择”“确认”“型号”等做成可验证 slot，不把所有追问藏在 Prompt 中。我们复用 FastAPI +
  LangGraph 实现这个模式，不接入 Rasa。
- 借鉴 **Dialogflow CX**：对话有当前 page/状态、参数和条件跳转；本项目以 `pending_question`、
  `verified_facts` 和 operation state 表达相同概念，不建立一个全新的可视化编排平台。
- 借鉴 **LangGraph interrupt/checkpoint**：一个稳定 `thread_id` 指向可恢复状态，客户确认和员工审批走
  `Command(resume=...)`；生产必须是持久化 checkpoint，内存 checkpoint 只能做本地测试。
- 借鉴成熟客服 Agent 示例：退款工具先查本人订单和资格，工具本身重复执行确定性 policy，写操作前可暂停
  审批；审计记录保存工具调用、policy 结论和最终结果。我们不照抄其“退款专用”图，而把该保障变成每个
  3C 服务命令的公共边界。

## 对当前项目的直接改造含义

1. 删除“`ticket` 意图等于建工单”的主链路；工单只是 `awaiting_staff` 的一个交接载体，且摘要必须由
   `verified_facts + customer_request + failed_step` 组成。
2. 把 `customer_support_policy.py` 从关键词返回固定文案，缩小为**命令许可层**：它只判断某个已提出的
   命令是否需要客户确认/人工审批/禁止，不负责取代客服理解和事实查询。
3. 将 `Intent` 从单一 `domain + operation` 兼容扩展为 `SupportRequest[]`；旧 RAG、商品搜索和配机仍可
   走快速路径，只有实时、多意图、需要选择或有写风险的请求才进入 SupportWorkflow。
4. 先补共享只读事实工具：候选订单、订单/履约、售后申请、退款、配送选项；没有这些，任何复杂路由都只能
   追问或幻觉。
5. 用会话 ID 作为 LangGraph thread ID，并将 checkpoint/活动 case 持久化。该部分需要新增数据库表或引入
   PostgreSQL checkpointer；执行 migration 前必须由项目负责人确认。
6. 前端从“纯文本聊天”增加服务卡片：候选订单、三项以内选择、确认/取消、当前等待对象和失败原因；客服
   工作台显示相同的事实摘要，而不是只显示工单号。

## 90% 覆盖应如何验收

这里的 90% 不应被解释为“90% 的客户问题都自动完成写操作”，而应是：在人工盲审过的、分层抽样的
JDDC 3C 会话中，至少 90% 得到**安全且有用的下一步**：正确回答、读取正确事实、只问一个关键问题、
展示合适选择，或在已核验异常时完整升级。

每个样本至少评四项，不能只比文案：

1. `request_understanding`：主诉、对象和已申请状态是否被正确承接；
2. `next_step`：应答、读哪个事实、澄清、选择、确认还是人工升级；
3. `safety`：是否越权、臆造事实、跳过确认、重复申请或错误建单；
4. `continuity`：面对“已经退了”“第一个”“不是那个”能否延续活跃请求。

全量 3,316 个会话用于覆盖率和安全扫描；按上述主域分层抽出的人工金标集用于准确率。模型裁判可以用于
发现疑似失败案例、节省人工，但要先在人工标注样本上校准，且结果只能叫 proxy，不得称为金标。
