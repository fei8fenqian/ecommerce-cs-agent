# E-Commerce-Agent Architecture — Demo Baseline

## Goal

This repository is a modular monolith for an interview-ready ecommerce Customer Agent.
Correctness and stability outrank feature count. The LLM should feel like a helpful store
associate; server code owns business identity, facts and actions.

## Customer Agent roles

```text
Customer Agent
      |
 Turn / Goal Router
      |
 +----+------------------+
 |                       |
Ecommerce Role       Service Role
 |                       |
Product Context      Support Case
ProductResolver      OrderSubjectResolver
Catalog Procedure    Order / Refund Workflow
 |                       |
 +----------+------------+
            |
      Tools / DB / Provider
            |
       Presentation
```

There is one conversational agent, not independent autonomous Product and Support agents.
Role state is isolated even though conversation history is shared.

## Ecommerce Role contract

`Product Context` owns only:

- hard constraints implemented for the demo: category and explicit numeric price bounds;
- soft preference history used for semantic comparison;
- the current server-owned product candidate frame;
- the currently selected canonical product.

Flow:

```text
User language
-> product goal/category
-> hard constraints
-> authoritative Catalog filtering
-> server-owned candidate frame
-> ProductResolver owns open-ended recommendation ordering / semantic selection inside that frame
-> Server validates every recommended/selected candidate ref
-> recommended refs may receive real product-detail actions without becoming selected state
-> explicit customer selection promotes canonical product identity
-> Server product action / URL
-> Operator explains naturally
```

Hard constraints decide eligibility. Brand/model wording and preferences such as learning use, board photography,
CPU/GPU/memory priority, light weight or battery preference are semantic evidence inside the eligible Catalog pool;
a mere brand mention is not automatically persisted as an exclusive filter. Business code must not add per-preference
ranking branches: the ProductResolver reasons from the user's language and the current product's public Catalog
attributes. Soft preferences cannot make an ineligible product enter the frame.

Recommendation and selection are distinct: a server-validated `recommended_ref` may get a real detail-page action,
but only explicit customer selection may become `selected_product` continuity. The final LLM answer is presentation,
never a protocol for selecting a product.

## Service Role contract

Phase A Order / Refund orchestration remains authoritative:

- Goal -> IntentRouter;
- Order Subject -> OrderSubjectResolver;
- real order binding / ownership -> Server;
- required reads -> Control Plane / Support Workflow;
- mutable order/refund truth -> Tool / Provider fresh reads;
- refund/navigation action -> Server;
- wording -> Operator LLM.

Ecommerce changes must not change these authorities.

## Cross-role rule

Context may cross roles; authority may not.

A recent selected product can help interpret "the phone I just bought", but Service Role must
resolve an authenticated real order before reading or acting on order/refund state. Product
candidate state never becomes an order subject.

## Non-negotiable invariants

1. Product and Support mutable state do not write each other's domain state.
2. Catalog truth beats model world knowledge for product identity, price and specifications.
3. Resolvers can select only opaque refs from a server-owned current candidate frame.
4. Router and Operator prose cannot create authoritative product/order IDs.
5. Server actions and URLs are generated by server code, never by the LLM.
6. Mutable financial/order/refund facts used as current truth require current authoritative provenance.
7. What the UI or Operator presents as a numbered product/order choice must preserve the exact server-owned candidate snapshot and order that the server validates.
8. Product changes must pass Phase A Order/Refund regression tests before merge.

## Demo stop gate

Phase B is complete when these work in real multi-turn API/browser E2E:

- a price range such as 4000-5000 produces no candidates outside that range;
- learning / board-photo preferences recommend only current Catalog candidates;
- a model with multiple variants remains ambiguous until the user chooses one;
- a selected variant becomes a canonical server product;
- every server-validated recommended product can expose its specific detail-page action immediately;
- "give me the link" for a discussed/selected product opens the specific product detail page, not a generic catalog page;
- after purchase, "I just bought this but want to return it" switches to Service Role and the
  Phase A order/refund workflow still resolves the authenticated order correctly.

Large framework rewrites, generic domain engines, microservices and full Phase C cleanup are out
of scope until after the interview demo is stable.
